## 1. P15 · 缺陷收口（v6.28）

### 1.1 P15-1 重置漏清计划标记（实测缺陷）

**现象**（10-31 实测，390×900，`planOnly=true`，`gearMarks={"1":{g:16}}`）：

```
点「重置档位状态」→ 确认
MARKS before/after reset: 1 → 1      ← 没清
回到建仓页：pill 仍是「已买入」「估」
```

确认框原文是「清空全部买卖记录与档位状态？参数保留。」—— 用户的理解必然是标记也没了。

**根因**：`index.html:6991` 的 `btnReset` 清空列表有
`gearsDone / gearHit / gearCleared / feed / buys / sells / swingGears / dripAt`，
**唯独没有 `gearMarks`**。这是 P6 §12.4 挂下来的「清空数据是否该连 gearMarks 一起清」，一直没定，于是既不清也不算错。

**改法**：

```javascript
S.cfg.gearMarks = {};   /* P15：计划模式的执行标记，同样是"记录"不是"参数" */
```

同时把确认框补一句：`参数保留，计划模式的已买入标记一并清空。`

**边界**：`marks`（自定义价位）/ `alerts`（提醒）/ `takePlan`（止盈计划）**不清** —— 这三个是用户手设的"参数"，与"记录"不同。文案已经写了"参数保留"，行为一致。

## 2. P16 · 结构页通道图 1 小时（v6.29）

### 2.1 现状

通道图只有两枚周期 chip（`index.html:713-714`：`1d` 默认、`4h`），但**1 小时 K 线一直在拉**（`PERIODS` 里 `1h` limit 1000，`fetchKlines` 遍历全部四周期），数据现成。

四处硬编码挡着：

| 位置 | 代码 | 问题 |
|---|---|---|
| `renderChart():4521` | `var label = k === "4h" ? "4小时" : "日线";` | 1h 会显示成"日线" |
| `chMeta` 文案 | `label + " · 90 根"` | 同上 |
| 刻度 | `fmtDay(d[0].t)` → `MM-DD` | 1h 的 90 根跨 3.75 天，同一天出现多次，看不出是几点 |
| `aria-label` | `label + "回归通道图"` | 跟随 label，改 label 即可 |

### 2.2 改动

1. `#chChips` 加第三枚：`<button data-p="1h">1小时</button>`，顺序 日线 / 4小时 / 1小时
2. label 换成映射表：

```javascript
var CH_NAME = { "1d":"日线", "4h":"4小时", "1h":"1小时" };
var label = CH_NAME[k] || "日线";
```

3. **窗口按周期分别设**（细则见 §2.3）：

```javascript
var CH_WIN = { "1d":90, "4h":90, "1h":180 };
var win = CH_WIN[k] || 90;
var ch = channelOf(bars, win, S.price);
```

4. 新增 `fmtHM(t)` → `MM-DD HH`；1h 时左右刻度用它，1d/4h 仍用 `fmtDay`
5. `chanText(ch, label)` 已经接受 label 参数，传对即可，函数体不动

### 2.3 窗口按周期分别设，不统一 90 根（已定）

`channelOf(bars, n, price)` 的 `n` 是**根数**不是天数。统一 90 根会让 1h 只覆盖 3.75 天 —— 不到四个交易日，看不出结构，这个切换等于白给。所以窗口按周期各设：

```javascript
var CH_WIN = { "1d":90, "4h":90, "1h":180 };
```

| 周期 | 窗口 | 折合时间 | 通道含义 |
|---|---|---|---|
| 日线 | 90 根 | 90 天 | 中期趋势走廊（不变） |
| 4小时 | 90 根 | 15 天 | 短中期（不变） |
| **1小时** | **180 根** | **约 7.5 个交易日** | 短期走廊，次日级别的波动 |

时间跨度形成 `90 → 15 → 7.5` 的梯度，每级约减半，1h 与 4h 相邻可比。

#### 为什么定 180 根，不是 240 或 360

绘图区固定 `viewBox="0 0 360 190"`，`padL=6 / padR=46` → 绘图宽 **308 逻辑像素**，每根占 `308 / n`；蜡烛宽 `max(1.2, step*0.62)`，所以根数超过某点后蜡烛不再变细、开始互相挤压：

| n | 每根占宽 | 蜡烛实际宽 | 缝隙 | 观感 |
|---|---|---|---|---|
| 90 | 3.42px | 2.12px | 1.30px | 清楚 |
| 120 | 2.57px | 1.59px | 0.98px | 清楚 |
| **180** | **1.71px** | **1.20px** | **0.51px** | 每根可分辨（采用） |
| 240 | 1.28px | 1.20px | 0.08px | 糊成色带 |
| 360 | 0.86px | 1.20px | **−0.34px** | 蜡烛互相覆盖 |

180 是"每根还看得出"的上限附近。再往上加，蜡烛宽被 `max(1.2, …)` 卡死、缝隙消失。所以 1h 取 **180**：跨度从 3.75 天翻到 7.5 天，可读性还在。

**以后若想在 1h 上看更长历史**，正确做法是换更宽的 `viewBox`（例如 1h 用 `0 0 720 190` 并横滑），不是继续加根数 —— 加根数只会把蜡烛压成一条色带。

#### 标签与说明

- `chMeta` 显示**各周期的真实根数**：`日线 · 90 根` / `4小时 · 90 根` / `1小时 · 180 根`
- 卡片 note 写清折算，避免"根数一样长"的误读：

> 回归窗口：日线 90 根（90 天）、4小时 90 根（15 天）、1小时 180 根（约 7.5 个交易日）。短周期噪声大，r² 偏低时提示"弱上行 / 弱下行"是正常的。

- 1h 跨周末有约 48 小时缺口，左右刻度取 bar 的真实时间，不是等间距日历
- `chanText()` 里的 `pos / widthAtr / touchUp` 全是相对量，换窗口不需要改算法

### 2.4 技术坑

- `S.chPeriod` 只存内存（`:6757` 注释「设备偏好，只存内存，不写云端」），加 1h 不用改存储
- 1h 数据在周末有约 48 小时缺口，**180 根约跨 9–10 个自然日**；刻度按 bar 的 `t` 取，不受影响
- `channelOf` 的 `atrOf(d, 14, m-1)` 用的是窗口内最后 14 根 —— 1h 下即 14 小时，`widthAtr` 是"通道宽 = 多少个 14 小时 ATR"，与日线的"14 天 ATR"不同口径但比值可比
- 残差分位从 90 个点变 180 个点，上下轨更平滑；`pctile` 取整索引会落在不同位置，同一段数据换窗口结果必然不同，**这是预期的**，不要拿 1h 的 `widthAtr` 去对日线的值
- `body.kb`（输入框聚焦时底栏上移）与通道图无关
- 320 宽下三枚 chip 要验证不溢出：现有 `.fchips` 是 `overflow-x:auto` 横滑容器，理论上安全，但 P14 的 `OVERFLOW_JS` 已豁免横滑容器后代，得确认页面 `scrollWidth` 没变

### 2.5 验收

- 三枚 chip 可切，`#chMeta` 分别显示 `日线 · 90 根` / `4小时 · 90 根` / `1小时 · 180 根`
- 1h 下 `#chSvg` 里 **180** 根蜡烛，`aria-label` 为「1小时回归通道图」
- 1h 下左端刻度含小时（`MM-DD HH`），右端同
- 1h 与 4h 的蜡烛根数不同（180 vs 90），日线仍是 90（证明窗口按周期取，不是全局常量）
- 1h 蜡烛的左边界不与相邻蜡烛重叠（`step - pw >= 0.4px`）
- 切到 1h 再切回 1d，`chMeta` 与蜡烛数回到初始值（无残留）
- 320 / 390 宽：三枚 chip 不撑宽页面（`scrollWidth <= vw + 1`）
- `chanText` 里没有出现"日线通道"字样（1h 时）

测试：`test_p16_chart_1h.py` **8 条**。

## 3. P17 · 设置页收尾（v6.30）

P14 把设置页从 3839px 压到 2881px、加了速览条和折叠。但有三处是**实测出来的真问题**，不是审美。

### 3.1 P17-1 保存按钮离它作用的字段 1900px

实测坐标（390×844，10 档 + 计划模式）：

| 元素 | y | 说明 |
|---|---|---|
| 「目标总克重」输入框 | 173 | 需要保存 |
| 「建仓高点」输入框 | 480 | 需要保存 |
| 「目标均价」输入框 | 615 | 需要保存 |
| **「保存参数」按钮** | **2499** | 保存上面这 5 项 |

改完总仓要往下划 **2300px** 才够得着保存，而中间隔着的卡 C 全是"改即存"的控件 —— 用户很容易以为"我改的东西也自动存了"。

**改法：不挪原位按钮（你说过留一个），另加一条"未保存提示条"**，只在有脏值且滚动到看不见按钮时浮出，位置 `bottom: calc(56px + env(safe-area-inset-bottom))`（tabbar 高度 56px + 安全区，`:144` 已确认）。

```
┌──────────────────────────────┐
│ ● 2 项未保存      点此保存    │  ← 浮条，橙色左边框
└──────────────────────────────┘
```

- 未保存改动为 0 时**不渲染**（不占空间）
- 点击 = 调原来的保存逻辑，不复制一份
- `body.kb`（键盘弹起、tabbar 上移）时同步隐藏浮条，避免与键盘打架

### 3.2 P17-2 未保存状态根本看不见（比 3.1 更严重）

实测：

```
改 #setTotal = 500 → 切到总览 → 切回设置
输入框显示：500
cfg.TOTAL  ：310        ← 实际没生效
```

输入框**看起来已经改了**，实际引擎读的还是 310。这不是"值回退"，是"假装生效"，比回退更糟 —— 用户不会想到再点保存。

**根因**：`renderSet()` 只写初始化值，不重置这 5 个输入框；`compute()` 读 `cfg`，两者从此各走各的。

**改法：脏值检测**（不是回退输入）。

```javascript
/* 保存项的 cfg 值 vs 输入框值；不一致 = 脏 */
var SAVE_KEYS = [
  { id:"setTotal", key:"TOTAL" },
  { id:"setKeep",  key:"keepGram" },
  { id:"setHigh",  key:"H_BASE" },
  { id:"setAvgT",  key:"avgTarget" },
  { id:"setAvgBand", key:"avgBand" }
];
function dirtyCount(){ /* 逐项比，NaN 与空串都算"未改" */ }
```

- `refreshAll()` 末尾更新浮条与计数
- 输入框描边转橙色（`.fld input.dirty`）
- **切 tab 不重置输入框**：用户可能只是去总览看一眼再回来接着改，强行回退会更烦；标脏已经说清"还没生效"

### 3.3 P17-3 档数控件离它影响的分布 1.8 屏

`setGearCount(n)` 里有 `S.cfg.wPct = gearTemplate(n)` —— **改档数会整体重置权重分布**（P9 的既定语义）。

但「档位数量」在卡 B 末尾（y=1129），「档位分布」在卡 C 顶部（y=1311），中间隔着卡 B 的最后一项和两个卡头。用户改完档数往下划，才发现分布被换成了模板。

**改法：「档位数量」整块移到卡 C 顶部，紧跟「档位分布」之上**。同一屏内因果可见。

- DOM 移动，`#setGearCount` / `#setGearCountLive` 的 id 一律不动，P9 的 21 条测试不受影响
- 卡 B 摘要里的「10 档」仍读 `gearCount()`，不受位置影响
- 卡的语义更顺：卡 B 只管"形态"（高点 → 起点跌幅 → 第 1 档价 → 档距 → 锚定），卡 C 管"分几档、怎么分、怎么执行"

### 3.4 验收

- 改任一保存项 → 浮条出现且计数 = 实际脏项数；点保存 → 浮条消失、`cfg` 同步
- 切 tab 往返后输入框保留用户输入，浮条仍在（不再"假装生效"）
- 键盘弹起时浮条隐藏
- 「档位数量」在卡 C 首项，与「档位分布」同屏（390 宽下 y 差 ≤ 260px）
- 320 / 390：浮条不遮 tabbar、不溢出
- 设置页总高变化 ≤ ±80px（浮条是浮层，不占流）
- 573 条老测试一条不改

## 4. P18 · 复盘：计划 vs 实际（v6.31）

### 4.1 先说一条会决定整张表能不能做的约束

**两边币种不同**：

| 来源 | 记录单位 | 代码 |
|---|---|---|
| 计划模式 `gearMarks[i].cost` | **美元金额**（`gramToUsd(g, px)`） | `:1937` |
| 账本模式 `buys[].priceCny` | **元/克** | `:6578` |
| 档位价 | **$/oz** | `gearPrices()` |

计划模式可以换算到 $/oz（`:5123` 已有先例）：

```javascript
var avgOz = gearCost(i, mk) / gross * OZ_PER_G;   /* 美元/克 → 美元/盎司 */
```

账本模式做不到 —— 元/克 转 $/oz 需要汇率，而项目明确定过「不做人民币换算」（PRD §3.1）。

**结论**：偏差列**只在计划模式**提供；账本模式显示实际均价（元/克）与计划价（$/oz）两列并排，偏差写「—」，并给一句说明。不做假换算。

### 4.2 P18-1 逐档对照表

放在**持仓页**（`pos`）新增一张「执行复盘」卡，每档一行：

| 列 | 计划模式 | 账本模式 |
|---|---|---|
| 档位 | 第 3 档 | 第 3 档 |
| 计划价 | 4029.0 $/oz | 4029.0 $/oz |
| 成交均价 | 4041.2 $/oz | 129.8 元/克 |
| 偏差 | +0.30% | — |
| 克重 | 计划 48 / 实买 38 | 计划 48 / 实买 38 |
| 状态 | 待补 10g / 已买满 / 超买 X | 同 |

汇总行：`6 档已执行 4 档 · 计划均价 4088.1 → 实际 4102.3（+0.35%）· 总投入 $12,430`

偏差的着色：国内习惯，**成本高于计划 = 不利 = 绿**（省钱才是红？）。这里要小心：
- 这不是涨跌，是"买贵了/买便宜了"。买便宜是好事。
- 用中性色更稳：`|偏差| ≤ 0.5%` 灰、买贵 > 0.5% 橙、买便宜 > 0.5% 绿。
- 但用户可能按股票习惯读红绿。**建议：买贵橙、买便宜绿，不用红**（红在页面里专指"涨/亏损"，容易误读）。

### 4.3 P18-2 循环档统计（顺手接上，你没点但数据现成）

`planSummary()` 的 `grossBought / soldTotal / realizedTotal` 三个字段算了半年没人用（P15 只加注释）。同一张卡的顶部给 4 个数字：

```
累计买入 168g · 累计卖出 32g · 已实现差价 $412 · 周转 6 次
```

- 周转次数 = Σ `gearMarks[i].turns`（P6 已有）
- 差价单位用 **$**（与全站 $/oz 一致，不做人民币换算）
- 只在计划模式显示；账本模式这块显示「账本记录的是元/克，总计见上方持仓卡」

### 4.4 验收

- 计划模式：4 个数字与 `planSummary()` 一致；表格行数 = `gearCount()`
- 账本模式：偏差列为「—」，有说明文案，不出现 NaN / Infinity
- 空数据（全部未买）：表格显示"还没有执行记录"，不崩
- 单档超额：状态列显示「超买 X g」
- 10 档：表格可横滑或折行，320 宽不撑宽页面
- 累计值与档位行各自算的 `realized` 之和一致（防两套算法）

## 5. P19 · 历史回溯（v6.32）

### 5.1 先划清"回溯"的两种含义

PRD-v2 写的是「用 K 线重算过去 N 天的判定，验证策略可复现」，这句话其实是两件事：

| | 做什么 | 回答的问题 | 成本 |
|---|---|---|---|
| **P19-1 判定回溯** | 对历史每一天重跑 `judgeOne()`，输出方向序列 | 「当时页面说的是上行，真的是上行吗」 | 小 |
| **P19-2 策略回测** | 按当前档位参数逐日模拟买入，算收益 | 「这套阶梯在过去一年赚不赚钱」 | 大 |

**建议分两期**，P19-1 先上（它同时是 P19-2 的地基），P19-2 看 P19-1 的体感再定。

### 5.2 P19-1 判定回溯

**利好**：`judgeOne(bars)` 是纯函数（`:1396`），只看 `bars` 最后一根，不碰全局 `S`。回测 = 对每个 i 传 `bars.slice(0, i+1)`。

**硬约束：能回溯多久取决于数据根数**

| 周期 | 现有根数（`PERIODS`） | 判定预热需求 | 可回溯 |
|---|---|---|---|
| 日线 | 800 | `computeStruct` 要求 ≥ 210 根 | **590 天** |
| 4小时 | 750 | 同上 | 540 根 ≈ 90 天 |
| 1小时 | 1000 | 同上 | 790 根 ≈ 33 天 |
| 四周期共振 | — | 受最短的 1h 卡住 | **仅最近 33 天** |

**所以要诚实标注**：日线方向可以回看 590 天，四周期共振只能回看 33 天。UI 上直接写「共振回溯受 1 小时数据限制，最多 33 天」。

**实现要点**：

```javascript
function judgeAt(bars, i){
  if(i < 209) return null;                  /* 预热不足 */
  return judgeOne(bars.slice(0, i + 1));    /* judgeOne 只看最后一根 */
}
```

- 800 次 × `judgeOne`（含 MA200 / MACD / ADX），估 40–80ms，可同步跑；超过 200ms 就分帧（`requestAnimationFrame` 每帧 50 根）
- 输出：近 N 天方向序列（上行/震荡/下行）+ 每次"方向切换"的日期
- 可测性：固定 fixture 的 K 线，断言某一天的 `state` 与手算一致；同一天跑两次结果必须相同

### 5.3 P19-2 策略回测

按当前参数（档数、起点跌幅、档距、权重、总仓），逐日模拟：

```
对每一天 i：
  取当日最低价 low
  for 每一档未触发的档位：
     if low <= 档位价 → 按 plan 克重记一笔买入（成交价 = 档位价）
  记录：累计投入、持仓克重、当日市值（用收盘价）
输出：触发次数、总投入、平均成本、期末浮盈（%、$）、最大回撤
对照：同期等额定投 / 期初一次性买入
```

**必须声明的简化**（写进页面 note，不能装成"精确回测"）：

1. 不看盘中路径，只看最低价是否触及（一天内先跌后涨还是先涨后跌，结果一样）
2. 不扣手续费、点差
3. 不模拟循环档的卖出（P19-2 先只算建仓档；循环档的买卖需要"卖出价"规则，P6 的规则是反弹到上一档卖出，可以后续加）
4. 买入价取档位价，不取当日最低（保守）
5. 不重分配（P8 的下沉逻辑不参与，否则状态机太复杂）

**这几个"不"就是它的价值边界**：回测结论只能回答"这套档位在历史波动里大概是什么体感"，不能当成精确收益预测。

### 5.4 验收

P19-1：
- 日线回溯 590 天，「方向切换」次数与逐日手工比对一致
- 同参数跑两次，结果逐值相同
- 共振回溯区间 ≤ 33 天，超出时给提示而不是静默截断

P19-2：
- 固定 fixture：某段已知 K 线上触发 3 次，手算总投入一致（±0.5%）
- 空区间（未触发任何档）：显示"区间内未触及任何档位"，不崩
- 三个对照数字（策略 / 定投 / 一次性）都在同一区间、同一本金口径

测试：`test_p19_backtest.py` **22 条**（10 + 12）。
