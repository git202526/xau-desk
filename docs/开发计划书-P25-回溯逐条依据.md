## 零、现状：数据全都有，就是没显示

`judgeOne()` 每次返回的是完整判定：

```js
{ state, upN, dnN, upC, dnC, c, ma5, ma20, ma60, ma200, rsi, rsiState, macd, adx, atr, hi20, lo20 }
```

其中 `upC` / `dnC` 各是 5 条 `{ k: 条件名, v: 是否命中, d: 数值说明 }`。

但 `btRun()` 存序列时只留了三样：

```js
seq.push({ i:i, t:bars[i].t, c:bars[i].c, state:r.state, hits:hits, names:names });
```

`names` 还是「最多 3 个命中条件名」。所以点某一天只能看到：

> `10-28 · 上行 · 命中 4/5（收盘站上 MA20、MA5 上穿 MA20 上方、近 20 根高点抬高，共 4 条）`

用户没法回答最该问的那句：**没命中的那条，差多少？**

## 一、设计

### 1.1 不扩缓存，点击时现算

```js
function btDetail(idx){
  var k = S.btPeriod || "1d";
  var bars = (S.kl || {})[k];
  var seq = btRun(k);
  if(!bars || !seq || !(idx >= 0) || idx >= seq.length) return null;
  var i = seq[idx].i;
  if(i < BT_WARM) return null;
  return judgeOne(bars.slice(0, i + 1));     // 单次 ~10ms，可接受
}
```

**为什么不把 detail 塞进 seq**：800 天 × 5+5 条 × 两个字符串，会把缓存从几十 KB 撑到上 MB，而且 99% 的格子一辈子不会被点。现算一次 10ms，比常驻内存划算。

### 1.2 详情区结构

`#btPick` 从「一行文字」扩成「摘要 + 逐条 + 指标」：

```
┌──────────────────────────────────────────┐
│ 10-28 · 上行 · 命中 4/5                    │  ← 摘要行（原有一行保留）
├──────────────────────────────────────────┤
│ ✓ 收盘站上 MA20      现价 4,120.5 / MA20 4,080.2 │
│ ✓ MA5 上穿 MA20 上方  MA5 4,095.1 / MA20 4,080.2 │
│ ✗ MA20 拐头向上      前值 4,085.0 → 现值 4,080.2 │
│ ✓ 近 20 根高点抬高   4,150.0 → 4,180.0     │
│ ✓ ADX≥20 且 +DI 占优  ADX 24.3 · +DI 28.1 / -DI 19.4 │
├──────────────────────────────────────────┤
│ 另一侧 1/5 ｜ RSI 58.2 偏强 · ATR 18.4     │
└──────────────────────────────────────────┘
```

规则：

- **显示哪一侧**：与摘要一致 —— 上行显示 `upC`，下行显示 `dnC`，震荡显示命中较多的那一侧（`btRun` 里已有同样的取舍逻辑，复用 `side` 计算）
- **✓ / ✗** 用两色：命中走 `--up` 色系（红，本页涨），未命中走 `--tx3`（灰）。**不用绿**（绿在本页是跌）
- **数值说明**取自 `judgeOne` 的 `d` 字段，一个字都不重新拼
- **指标行**固定显示：另一侧命中数、RSI（带状态词）、ATR14
- 数据不足（`i < BT_WARM` 或越界）→ 隐藏详情区，不显示半张表

### 1.3 样式

全部走 class（`.btpk-row` / `.btpk-ok` / `.btpk-no` / `.btpk-meta`），不写内联 `style`。320 宽下每行允许换行（`display:flex; gap:6px; flex-wrap:wrap`），`d` 那一列不截断。
