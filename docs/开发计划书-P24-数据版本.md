## 零、现状与问题

P20 的迁移长这样：

```js
if(cfg.migratedV7) return false;   // 一个布尔，代表「第 7 版数据已迁移」
```

调用点有 **4 处**，每处都在不同的数据到达时机上：

| 行 | 位置 | 为什么在那里 |
|---|---|---|
| 5259 | `applyRemote()` | 云端数据落库 + `compute()` 之后，`planOf()` 才有数 |
| 5283 | `doPull()` 合并分支 | 本机抢先记账、云端未载入时的合并路径 |
| 5304 | `doPull()` catch 分支 | 断网退只读快照 |
| 7837 | `refreshPrice()` 的 `fetchFx().then()` | 汇率到位后补跑（带档记录的 `priceCny` 折美元要用 `S.fx`） |

问题有三个：

1. **加一次迁移就要再复制 4 遍**，而且第 4 处（汇率门）最容易被漏掉
2. **`migratedV7` 是个布尔，不是版本号**。下一次迁移只能叫 `migratedV8`，再下一次 `migratedV9`，字段越堆越多，也不知道「现在整体是第几版」
3. **没有「未完成」这个状态**。汇率没到时迁移只做了一半，靠「不置 `migratedV7`」隐式表达，读代码的人很难看出来

## 一、设计

### 1.1 版本号

```js
var SCHEMA = 1;                    // 当前数据版本；每次结构变更 +1
```

`S.cfg.schemaVersion`（数字，缺省视为 0）。**不删 `migratedV7`** —— 老用户数据里已经有它，删了会重跑迁移；保留作为「v1 是否完成」的内部标记。

### 1.2 唯一入口

```js
function runMigrations(){
  var cfg = S.cfg || (S.cfg = {});
  var from = Number(cfg.schemaVersion) || 0;
  if(from >= SCHEMA) return false;

  if(from < 1){
    migrateMarksV7();                 // 内部仍按自己的门（migratedV7 / 汇率）决定做多少
    if(!cfg.migratedV7) return false; // 没跑完 → 版本不推进，等汇率到位再来
    cfg.schemaVersion = 1;
  }

  if(Number(cfg.schemaVersion) > from) saveCfg();
  return true;
}

function migrateAll(){ return runMigrations(); }
```

**关键判断**：完成与否看 `cfg.migratedV7`，**不看 `migrateMarksV7()` 的返回值**。返回值是「这次有没有改动」——老用户已经迁移过时返回 `false`，但迁移其实是完成的。

### 1.3 四个调用点全部改为 `migrateAll()`

调用时机不变（仍是那四个时机），只是把函数名换掉。这样下一期加 v2 迁移时，只改 `runMigrations()` 一处。

### 1.4 `mergeRemote` 版本取 max

并集合并后 `out = Object.assign({}, remote, S.cfg)`，`preferLocal` 时本机覆盖远端。若本机 `schemaVersion=0`、远端 `=1`，合并结果会退回 0，导致重跑一次迁移（幂等，无害但多余）。

版本号是**单调递增**的，取 `max` 永远正确：

```js
out.schemaVersion = Math.max(Number(remote.schemaVersion) || 0, Number(S.cfg.schemaVersion) || 0);
```

### 1.5 未来版本容错

若读到 `schemaVersion = 99`（用户在新版页面存过数据，又回退到旧版页面），`from >= SCHEMA` 直接返回 false，**不做任何降级、不删字段**。旧页面照常渲染，只是不认识新字段——比清空配置好。

## 二、验收标准

`tests/test_p24_schema.py`，**8 条**：

| # | 断言 |
|---|---|
| v1 | 空配置首次加载 → `schemaVersion === 1` |
| v2 | 老数据（`buys` 带档 + 无 `gearMarks`）→ 生成标记，且 `schemaVersion === 1` |
| v3 | 同上但汇率不可用 → `schemaVersion` 仍为 0、`migratedV7` 未置；汇率到位补跑后 → 1 且标记正确 |
| v4 | 老数据已 `migratedV7=true`、无 `schemaVersion` → 标记**一个不改**，只把版本升到 1 |
| v5 | 连续调 `migrateAll()` 三次 → 标记与版本完全不变（幂等） |
| v6 | `mergeRemote(远端 v1, 本机 v0)` → 结果版本为 1（取 max） |
| v7 | `schemaVersion=99` → 不降级、不清字段、`runMigrations()` 返回 false |
| v8 | **源码断言**：`migrateMarksV7()` 作为独立语句的调用点只剩 `runMigrations` 内部 1 处（其余 4 处都已改名） |

> v8 是这一期真正的保险丝。它锁的不是运行时行为，而是「入口只有一个」这条结构约束——没有它，下一期很容易又在某个分支里补一个直接调用。

## 三、风险与回退

| 风险 | 处理 |
|---|---|
| 版本推进了但迁移没跑完 → 老记录永远不折标记 | 用 `cfg.migratedV7` 而非返回值判断完成；v3 专门锁这条 |
| 用户在两台设备间来回切换，版本回退 | `mergeRemote` 取 max；v6 锁这条 |
| 迁移改坏数据 | 迁移只写 `gearMarks`，不碰 `buys`/`sells`（P20 已定，本期不改） |
| 需要回退 | 删 `schemaVersion` 字段即可回到 P20 行为；`migratedV7` 还在 |
