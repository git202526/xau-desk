# 约束 · 代码与 DOM

> 动手改 `index.html` 之前先看一眼。这里每一条都是踩过坑才写下的，不是风格偏好。

## 一、`sanitizeHtml` 白名单（最容易踩）

用户输入的名称、备注、提醒文案都会过 `sanitizeHtml()` 再进 DOM。它用 `DOMParser` 解析后逐个节点白名单过滤，**不在名单里的一律删除**（不是转义，是删掉）。

**允许的标签（8 个）**：`DIV` `SPAN` `BUTTON` `I` `S` `B` `STRONG` `EM`

**允许的属性（5 类）**：`class` · `value` · `data-*` · `title` · `aria-label`

### 四条硬禁令

| 想写 | 会被删成 | 正确做法 |
|---|---|---|
| `<br>` 换行 | 空（两句粘成一段） | 多个 `<div>` 或 `<span>` + CSS `display:block` |
| `<table>` | 空（整张表消失） | flex / grid 布局的 `<div>` |
| `<div id="x">` | `id` 属性被剥，元素还在 | 用 `data-*` 定位，如 `data-rv="h"` |
| `style="..."` | 属性被剥，样式失效 | 全部写进 `<style>` 的 class |

### 已经踩过的两次

- **v6.37（P18）**：复盘卡页脚三句话用 `<br>` 分隔，页面上粘成一行。改成三个 `<div>`
- **v6.37（P18）**：逐档表格用 `<table>`，整张表被删空。改成 `div` 三行块 + `data-rv` 定位

> 判断方法：只要这段 HTML 可能来自用户输入，就假设它会被剥到只剩 8 个标签。宁可一开始就用 `div` + `class`。

## 二、内联零外链

- 不引 CDN、不引 web font、不引图表库
- 图表（K 线迷你图、权益曲线、仓位条、回溯色带）全部**内联 SVG 手写**
- 图标用**内联 SVG path**，不用 emoji、不用 icon font
- 唯一的网络请求是数据接口（行情 / K 线 / 汇率 / GitHub），不是资源

理由：这个页面的交付形态是「单个 `index.html` 也能量跑」。一旦引了外部 JS，用户保存下来的文件就是废的。

## 三、单文件与体量

| 指标 | 当前 |
|---|---|
| 行数 | ~8.9 千行 |
| 体积 | ~388 KB |
| gzip 后 | ~131 KB |

新增功能前先估算：**单次改动超过 300 行就要拆批**。总体超过 500 KB 时，考虑把不常用的折叠卡（设置页三卡、回测）做成懒渲染，而不是拆文件。

## 四、数据三层

| 层 | 存哪 | 谁写 |
|---|---|---|
| `S.cfg` 配置 | 云端 `data.json` | 设置页、档位参数 |
| `S.cfg.gearMarks` 档位执行 | 同上 | 标记面板、记账对账、减仓摊派 |
| `S.cfg.buys` / `sells` 账本 | 同上 | 买入 / 减仓表单 |

**派生数据不落盘**：执行复盘（`rvRows`）、策略回测（`btBack`）、判定回溯（`btRun`）都是每次现算，缓存只放内存（`_btCache` / `RV_SCANS`），刷新即弃。原因是它们随参数变，存下来必然与参数不一致。

## 四之二、钱一律人民币（P27）

标记层（`cfg.gearMarks`）一次成交是**三个独立事实**，互不推导：

| 字段 | 单位 | 来源 |
|---|---|---|
| `g` | g | 用户填 |
| `costCny` / `proceedsCny` | ¥ | 用户填（主口径） |
| `cost` / `proceeds` | $ | 由 `$/oz` 推导，**只用来算 `$/oz` 均价** |

三条硬规矩：

1. **页面上的「钱」都是 ¥**：已实现、每克拉低、阶梯表差价、兜底预估金额。写美元金额必须带 `$` 符号。
2. **`$/oz` 不参与任何货币换算**。只和档位价比「买贵了多少」，比完就结束。
3. **不知道就是 `null`，不是 `0`**。`gearRealized()` 在 `costCny = 0` 时返回 `null`；
   `0` 会被读成「不赚不亏」，两个结论必须分得开。所有调用点要能接 `null`，显示成「—」。

老数据不猜汇率：账本记录的 `priceCny` 是元/克，`克 × 元/克 = 元`，能精确补；
纯手工标记补不出来，留「¥未填」，不按当天汇率伪造。

## 五、刷新必须单向

```
交互 → 改数据 → refreshAll() → 各渲染函数各自读最新数据
```

- **渲染函数之间严禁互调**（`renderCalendar()` 调 `renderTodayList()` 这类）
- 需要联动时，在事件处理里改完数据统一调 `refreshAll()`
- 每个渲染函数必须能独立跑（空数据不崩、重复跑结果相同）

### 五之二、回测不读实盘状态（P28）

回测是「假设」，实盘是「事实」，两者共用一个 `S` 但绝不能互相写：

| 禁止 | 原因 |
|---|---|
| 回测里调 `planOf()` | 它会读 `S.price` / `S.reallocDead` 并**写回**，等于把今天的状态塞进回测起点 |
| 回测里读 `S.cfg.realloc.on` 决定是否下沉两次 | 设置与回测各一套开关会叠加，且用户看不出哪套算数 |
| `btOpts.realloc` 当布尔用 | 必须三态：`null` 跟随设置、`true/false` 明确覆盖 |

正确写法：

```js
var plan = planBase();                 // 纯权重，无状态
var eff  = useRealloc ? reallocPlan(plan, { buyOf, dead, price: cl, prices: pr }) : plan;
```

### 五之三、金额一律「克 ÷ 31.1035 × $/oz」（P28）

金价是 $/oz，克重是 g，**两者相乘没有意义**。任何「克 × 价格」的地方都要先除 31.1035：

```js
function btPxG(usdOz){ return usdOz / OZ_PER_G; }   // $/oz → $/g
var amt = gram * btPxG(px);
```

这个错误在回测里活了三个月，因为收益率分子分母同错，只有绝对金额放大 31.1 倍 —— 直到用户看到「本金 $826,800」才暴露。凡出现「本金 / 市值 / 已实现」三件套，先量纲后数值。

## 八、上线纪律（v6.44 起）

> 起因：v6.35～v6.43 九个版本、24 小时，只提交没推送，线上一直停在 v6.34。
> 当时的三个验收条件（用例全绿 / 全量通过 / `git status` 干净）**全都在本地闭环**，
> 没有任何一条会因为「没上线」变红 —— 848 条测试全都 `page.goto(localhost)`。

GitHub Pages 是 **push 即发布**，所以「提交」不等于「上线」。每期收尾固定三步，缺一步都不算完成：

| 步 | 命令 | 通过判据 |
|---|---|---|
| 1 | `python3 -m pytest -m smoke` | 19 条全绿 |
| 2 | `git push origin main` | `git rev-list --count HEAD...origin/main` 输出 `0	0` |
| 3 | `python3 -m pytest -m deploy` | 5 条全绿（含线上字节 sha256 比对） |

`tests/test_deploy_parity.py` 是这条纪律的执行体，`pytest.ini` 用 `addopts` 默认把它排除
（日常全量不联网），只有显式 `-m deploy` 才跑。五条的分工：

| 条 | 断什么 | 断了说明 |
|---|---|---|
| `d1` | 工作区无未提交改动 | 改完没提交 |
| `d2` | HEAD == 远端 main SHA | 提交了没推（本地引用领先必红，不依赖网络） |
| `d3` | 线上 HTTP 200 且体积正常 | Pages 挂了或没构建 |
| `d4` | 线上 sha256 == 本地 | 构建成功但不是这份文件 |
| `d5` | 版本号一致 | 同上，但给人话 |

三条硬规矩：

1. **汇报「完成」以第 3 步绿为前提**。只说「848 条通过」不算数，那是本地事实。
2. **版本号对不上先分清是哪种**：没推（`d2` 也会红）还是 Pages 还在构建（约 1～2 分钟，重跑即可）。不要急着重推。
3. **不要 force push 覆盖 `calendar.yml` 的自动提交**。远程每天会有 `chore: refresh calendar`，先合并（`calendar.json` 取远程），再推。

### 8.1 测试默认并行（v6.49 起）

904 条用例每条都要 `page.goto` 一次，固定成本 ≈0.6 秒，串行合计 18 分钟。这 18 分钟里
真正的断言只占一半，另一半是反复把同一个页面打开 904 次。

`pytest.ini` 因此默认带 `-n 8`（依赖 `pytest-xdist`）：

| 跑法 | 耗时 | 用途 |
|---|---|---|
| `pytest` | 约 4 分钟 | 日常全量，默认 |
| `pytest -n 12` | 2 分 52 秒 | 收尾全量 |
| `pytest -m smoke` | 8 秒 | 改一处看一眼 |
| `pytest -n 0` | 18 分钟 | 只在调试并发相关问题时用 |

**不要为了省时间改成「只跑改动相关文件」**。本项目的测试有 37/64 个文件直接读写
`window.__xt.state()`，`compute` / `refreshAll` / `gearState` 各被 12～14 个文件共用；
「关联范围」靠人判断一定会漏（P28 的量纲改动看着只影响回测，实际经由 `planOf()` 写回
污染了别处状态）。并行已经把全量压到 3 分钟，没有拿覆盖率换时间的必要。

并行下若出现只在并发时红的用例，先怀疑固定 `wait_for_timeout` —— CPU 争抢会让它提前
返回，表现为数值没更新（`assert 100 == 80`）。改 `wait_for_function` 条件等待，不要加大毫秒数。
