## 1. P4-1：档位双逻辑

### 1.1 现有逻辑为什么不够

当前 `computeGears()` 的做法是：

```
档位价 p_i = 基准 H × (1 + pct_i / 100)          // pct: -10, -12, -13 … -18
计划克重 g_i = 总仓 × w_i / Σw                    // w: 8, 12, 10, 40, 15, 15
推荐克重 = 剩余额度在「未完成档」之间按 w 重分
```

**H 是外生的**（D60 高点或手填），系统不知道「按这套档位买完，均价会落在哪里」。
结果就是你看到的现象：H 挂在 4480，1–4 档打完均价约 3800；而你心里的目标是 3950，
两者差 150 美元，整套档位其实「校准错了方向」，但页面不会告诉你。

### 1.2 新增逻辑的定义

**目标均价导向**：以用户设定的目标均价 `T`（美元/盎司）为锚，反解出一个**等效基准** `H_avg`，
让「第 1–4 档全部按计划成交」后的加权持仓均价正好等于 `T`。

- 仍然是 **2 个预警档 + 6 个建仓档**，档位百分比不变
- 主力克重仍然落在 **第 4 档**（w=40，占 40%）
- 5、6 档是「超跌追加」，会继续把均价拉低到 `T` 以下，这是设计意图，不是偏差
- **克重和持仓仍按人民币克价计算**；美元/盎司只用于档位定价与均价校验

### 1.3 反解公式

设 1–4 档的权重与回撤为 `w_i`、`r_i`，加权平均回撤：

```
r̄ = Σ(w_i × r_i) / Σw_i
   = (8×(-13) + 12×(-14) + 10×(-15) + 40×(-16)) / (8+12+10+40)
   = -1062 / 70
   = -15.1714%
```

1–4 档全成交的均价 = `H × (1 + r̄/100)`，令其等于 `T`：

```
H_avg = T / (1 + r̄/100) = T / 0.848286
```

一条乘除就完事，**不需要迭代求解**，也不改动权重结构。

### 1.4 数值示例（T=3950，容差 ±20，总仓 200 克）

`H_avg = 3950 / 0.848286 = 4656.6`

| 档位 | 回撤 | 触发价 | 计划克重 | 累计克重 | 累计均价 |
|---|---|---|---|---|---|
| 预警① | -10% | 4190.93 | — | — | — |
| 预警② | -12% | 4097.80 | — | — | — |
| 第1档 | -13% | 4051.23 | 16g | 16g | 4051.2 |
| 第2档 | -14% | 4004.67 | 24g | 40g | 4023.3 |
| 第3档 | -15% | 3958.10 | 20g | 60g | 4001.5 |
| **第4档** | **-16%** | **3911.54** | **80g** | **140g** | **3950.1 ✔** |
| 第5档 | -17% | 3864.97 | 30g | 170g | 3935.1 |
| 第6档 | -18% | 3818.40 | 30g | 200g | 3917.6 |

- **第 4 档打完：均价 3950.1，落在 3930–3970 区间内** ✔
- 全 6 档打完：3917.6，比目标低 32.4 —— 因为 5、6 档是更深的加仓，必然摊低均价

> 对照：若结构基准 H=4480，1–4 档打完均价 = 4480 × 0.848286 = **3800.3**，
> 比目标低 150。这就是现在这套档位「看着合理、买完却不在目标位」的原因。

### 1.5 两套逻辑的差异边界

| 维度 | 结构基准（现有） | 目标均价（新增） |
|---|---|---|
| 基准来源 | D60 高点 / 手填 H | 由 T 反解 |
| 回答的问题 | 「从高点跌到哪，值得买」 | 「按这套档位买完，均价会是多少」 |
| 适合场景 | 趋势跟随、有明确前高 | 有明确成本目标、要做网格/定投 |
| 权重结构 | 8/12/10/40/15/15 | **完全相同** |
| 档位百分比 | -10…-18 | **完全相同** |
| 止损/止盈/关键位 | 不受影响 | **不受影响** |

**关键**：只换「基准价 H 从哪来」，下游一行代码都不动。

### 1.6 克重分配：均价模式下要不要改

现有 `gram` 是「剩余额度在未完成档之间按权重重新分配」。这个策略在均价模式下有副作用：

> 假设第 1–3 档已买 60 克，剩余 140 克只能分给 4/5/6 档（w 合计 70）→
> 第 4 档会拿到 140×40/70 = **80 克**，比计划 80 克一致；
> 但若第 5、6 档也被手动标成已买，第 4 档就吃满 140 克，均价会被压到 3911 附近。

两个选项，请确认：

| 选项 | 规则 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | 均价模式下 `gram = plan × (剩余额度 / 总仓)`，按计划等比缩放 | 与「目标均价」自洽，买满 1–4 档即命中 | 剩余额度不足时，第 4 档买不满，需要提示「额度不足，无法达成目标均价」 |
| B | 沿用「剩余额度按权重重分」 | 代码零改动，能买满额度 | 均价可能偏离目标，与新模式的核心承诺冲突 |

结构基准模式**无论选哪个都保持现状不变**，避免回归。

### 1.7 数据结构

```js
cfg.gearMode  = "struct" | "avg"    // 默认 "struct"，老数据缺省即结构模式
cfg.avgTarget = 3950                // 美元/盎司，默认 null（未设）
cfg.avgBand   = 20                  // 容差 ±，默认 20
```

- 三个字段都进 `normCfg()`、默认 cfg、`isEmptyCfg()`（防止云端只有它们时被判空覆盖）
- `mergeRemote()` 沿用 `Object.assign` 的「本机优先」规则，无需墓碑（不是集合型数据）
- 不影响 `data.json` 现有结构，回退安全

### 1.8 计算层改动

```js
var MAIN_GEARS = ["第1档","第2档","第3档","第4档"];

/* 目标均价 → 等效基准 */
function avgBase(T){
  var ws = 0, wr = 0;
  GEARS.forEach(function(g){
    if(MAIN_GEARS.indexOf(g.name) < 0) return;
    ws += g.w; wr += g.w * g.pct;
  });
  if(!ws || !(T > 0)) return null;
  return T / (1 + (wr / ws) / 100);
}

/* 给定基准，算「前 N 档按计划成交」的加权均价 */
function planAvg(He, names){
  var gsum = 0, amt = 0;
  GEARS.forEach(function(g){
    if(names.indexOf(g.name) < 0) return;
    var grams = totalGrams() * g.w / wAll();
    gsum += grams; amt += grams * He * (1 + g.pct/100);
  });
  return gsum ? amt / gsum : null;
}
```

`computeGears()` 只改一行：

```js
var he = S.H_BASE || (computeHEff()||{}).h;          // 现在
var he = (S.gearMode === "avg" && avgBase(S.avgTarget)) || S.H_BASE || (computeHEff()||{}).h;
```

并把 `planAvg(he, MAIN_GEARS)`、`planAvg(he, ALL_GEARS)`、`avgBase` 一起挂到 `S.gears.meta`，
供渲染层与测试读取。

## 2. P4-2：事件日历补全

### 2.1 根因

`computeEvents()` 只有两类来源：

| 来源 | 覆盖 | 说明 |
|---|---|---|
| `FOMC_DATES` | 美联储利率决议 | 硬编码年度表，精确 |
| `firstFriday()` | 非农 | 规则推算，可靠 |

**CPI、核心 PCE、GDP、初请失业金、零售销售、ISM —— 一条都没有。**
所以你截图里今天 20:30 的两条 4 星（Advance GDP、Core PCE）在页面上根本不存在，
不是「抓取失败」，是**从来没写过这部分逻辑**。

### 2.2 数据源选型

| 源 | 跨域 | 含预期/前值 | 含星级 | 结论 |
|---|---|---|---|---|
| 金十 `datacenter-api` | ✗（502 + 无 ACAO） | 有 | 有 | 需签名头，不可用 |
| TradingEconomics | — | 有 | 有 | guest 账号已停用（410） |
| TradingView `economic-calendar` | 无响应 | 有 | 有 | 不可用 |
| **faireconomy / ForexFactory JSON** | ✗ 无 ACAO | **有** | **有（High/Medium/Low）** | **数据最全，需中转** |
| 自建规则推算 | — | 无 | 可给 | 只能兜底 |

**结论**：数据用 faireconomy（就是 ForexFactory 的官方周历），但它不给跨域头，
所以必须**在服务端抓、以同源静态文件交付**。

### 2.3 实施方案：GitHub Actions 定时抓取 → 同源 JSON

```
[GitHub Actions 每 6 小时]
        │  fetch ff_calendar_thisweek.json
        ▼
  精简 + 中英映射 + 时区归一
        │
        ▼
  calendar.json（公开仓库根目录，跟 index.html 同源）
        │
        ▼
[页面 fetch('calendar.json')] ──失败──▶ 回落到内置规则（FOMC + 非农）
```

**为什么放公开仓库**：私有仓库的 Pages 要付费；日历是公开数据，不涉及隐私。
`data.json` 仍在私有仓库，一点都不动。

**Actions 文件**：`.github/workflows/calendar.yml`

```yaml
name: refresh-calendar
on:
  schedule: [{cron: "0 */6 * * *"}]   # 每 6 小时，UTC
  workflow_dispatch:
jobs:
  fetch:
    runs-on: ubuntu-latest
    permissions: {contents: write}
    steps:
      - uses: actions/checkout@v4
      - run: python3 tools/fetch_calendar.py
      - run: |
          git config user.name  "calendar-bot"
          git config user.email "bot@users.noreply.github.com"
          git add calendar.json
          git diff --quiet --cached || git commit -m "chore: refresh calendar"
          git push
```

**产物格式**（`calendar.json`）：

```json
{
  "updatedAt": "2026-10-29T08:05:00Z",
  "week": "2026-10-25..2026-10-31",
  "events": [
    {"t": 1761745800000, "ccy": "USD", "name": "美国第三季度实际GDP年化季率初值",
     "en": "Advance GDP q/q", "impact": 4, "fc": "3.2%", "pv": "1.5%", "src": "ff"},
    {"t": 1761745800000, "ccy": "USD", "name": "美国9月核心PCE物价指数月率",
     "en": "Core PCE Price Index m/m", "impact": 4, "fc": "0.3%", "pv": "0.2%", "src": "ff"}
  ]
}
```

- `t` 统一为 UTC 毫秒时间戳，页面按本地时区渲染（和你截图里的 20:30 一致）
- 只保留 `USD / EUR / CNY / JPY`，`Low` 默认保留但折叠（可开关）
- 体积约 20–40 KB，不压缩也够小

### 2.4 中英映射与星级

- 内置约 40 条常见指标的中文名（GDP、PCE、CPI、非农、初请、零售、ISM、PMI、
  消费者信心、耐用品、房屋开工、ADP、JOLTS…）
- 未命中映射的保留英文原名，不猜、不机翻
- 星级：`High → 4`、`Medium → 3`、`Low → 2`；与金十的 4 星口径有出入（例如初请金十给 4 星、
  FF 给 Medium），以数据源为准，页面上标注来源，不硬掰

### 2.5 降级与过期提示

| 情况 | 表现 |
|---|---|
| `calendar.json` 取不到 | 回落到 FOMC + 非农，事件卡顶部提示「实时日历不可用，仅显示已知固定事件」 |
| `updatedAt` 超过 3 天 | 顶部黄条「日历数据 3 天未更新」 |
| `updatedAt` 超过 7 天 | 视为不可用，走回落逻辑 |
| 事件已过去 | 保留当天已公布的事件，标灰 + 「已公布」 |

### 2.7 一个必须提前说的限制

GitHub Actions 的 `schedule` **不保证准点**，高峰时会延迟几分钟到十几分钟，
极端情况会跳过某次。所以页面侧的「过期判定」必须有，不能假设文件永远新鲜。

另外本方案依赖 `nfs.faireconomy.media` 这个源，它没有 SLA。
一旦它挂了，回落到内置规则（FOMC + 非农），不会白屏。

### B.2 与计划书数值的偏差（三处，计划书的算术笔误）

| 项 | 计划书 | 实际 | 说明 |
|---|---|---|---|
| `avgBase(3950)` | 4656.59 / 4656.6 | **4656.45** | 3950 ÷ 0.848286 = 4656.45，计划书多了 0.15 |
| 第 4 档价 | 3911.54 | **3911.42** | 同上，由基准乘以 0.84 得出 |
| 全 6 档均价 | 3917.6 | **3917.47** | 同上 |

断言容差仍按 ±0.05 / ±0.5 执行，没有放宽；改的是被断言的数值本身，
因为它来自公式而不是估计值。若按计划书那个数写断言，实现「错」到能过测试才是问题。

### B.3 开发中定位并修掉的三个问题

1. **校验卡的命中判定恒为真**。1–4 档理论均价 = `H_avg × 0.848286`，而 `H_avg` 就是由
   目标反解的，所以它**必然等于目标**——拿它做命中判定，卡片永远显示「✓ 命中」，
   成了摆设（AV10 因此无法通过）。改成判定「已有持仓 + 后续按计划买入」的整体均价，
   只有这个口径才可能偏离。这是计划书设计上的漏洞，不是实现 bug。
2. **整体均价的档位范围算错**。第一版把 5、6 档也算进「后续买入」，导致无持仓时
   整体均价 = 3917.47（被超跌档拉低），直接判成偏离 32.5。改为只算 1–4 档，
   与「目标均价」的定义一致。
3. **替换函数时边界取错，删掉 1700 行**。用 `index("function computeEvents(){")`
   到 `index("function renderFeed(")` 做整段替换，但这两个函数在原文件里相隔 1700 行
