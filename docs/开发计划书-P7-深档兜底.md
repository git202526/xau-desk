# 开发计划书 · P7 深档兜底（v1.0）

> 范围：本文档只做设计，**不含任何代码改动**。确认后按 §8 分期开工。
> 前置状态：v6.19（P6 循环档）已实现、全量 343 条测试通过，**改动仍在工作区未提交**。

---

## 0. 一句话

建仓档（3–6 档）等太久就永远不会成交，给一条**到期提示 + 一键按现价买一半**的出路 —— 只提示，绝不自动下单。

---

## 1. 为什么做这个（问题已在 P5 §13 量化过）

以基准参数（H=4700、总仓 200g、档距 48）为例：

| 档位 | 档位价 | 计划克重 | 累计克重 | 只买到这档时的累计均价 |
|---|---|---|---|---|
| 1 | 4089 | 16 g | 16 g | 4089.0 |
| 2 | 4041 | 24 g | 40 g | 4060.2 |
| 3 | 3993 | 48 g | 88 g | 4023.5 |
| 4 | 3945 | 72 g | 160 g | 3988.2 |
| 5 | 3897 | 24 g | 184 g | 3976.3 |
| 6 | 3849 | 16 g | 200 g | 3966.1 |

买满 6 档是**低频事件**：40 日内从现价再跌到位只有 13.6% 的概率（P5 §13.1 实测）。剩下 86% 的时间，仓位停在 88–160g，均价停在 3966–4023 —— 而且每少买一档，均价就高 12–36 美元。

于是有两种坏结局：

1. **钱趴着**：160g 的计划额度挂在那里，几个月不成交，资金效率为零。
2. **均价不兑现**：目标均价靠深档拉，深档不来，目标就是一句空话。

P6 解决了「浅档能不能反复用」（能，循环档）。P7 解决「深档一直不来怎么办」（给一条有时间约束的兜底出路）。

---

## 2. 边界

### 做

- 建仓档计时：从「成为下一个待买档」那天起算，超过 `dripDays` 天且价格在容忍范围内 → 档位行内出现一条提示
- 一键执行：按现价买入「当前待补克重的 `dripPct`」，写完 `gearMarks`，计时重置
- 三个可调参数：等待天数、兜底比例、溢价容忍
- 只对建仓档生效（循环档走 P6 的买卖，不需要兜底）

### 不做

| 不做 | 原因 |
|---|---|
| 自动下单 / 自动写标记 | 系统不替你决定。必须人手点一下 |
| 后台定时提醒 / 推送 | 纯前端静态页，没有后台，也拿不到通知权限 |
| 兜底时自动降低目标均价 | 均价是结果，不是可以随便改的参数 |
| 多次兜底后自动清空该档 | 每次只吃一半，剩下一半继续等，这是设计要求 |
| 账本模式的兜底 | 账本记的是已发生的事实，不存在「等太久」这回事 |

## 3. 数据模型

### 3.1 新增配置

```js
cfg.dripDays       = 30    // 等待天数，0 = 关闭兜底；有效范围 7–180
cfg.dripPct        = 0.5   // 每次兜底吃掉「待补」的比例，0.1–1
cfg.dripMaxPremium = 3     // 现价高于档位价的容忍百分比，超过则不提示
cfg.dripAt         = {}    // { "4": 1761753600000 } 每档计时起点
```

四个字段全部有缺省值，老数据零迁移 —— 读不到就用默认，不需要写回。

### 3.2 `dripAt` 清洗

```js
/* 档号越界、时间戳非数或未来时间、该档已买满 → 一律剔除，绝不抛异常 */
function cleanDripAt(o){ ... }
```

规则：

- key 必须是 `1`–`6` 的整数字符串
- value 必须是 `> 0` 且 `<= Date.now() + 60s`（容忍轻微时钟漂移）的数
- 该档 `boughtOf(i) >= planOf()[i-1] - 0.05` 时**强制删掉**（已买满不该还在计时）

### 3.3 与 P6 的关系

- 复用 `gearMarks` 四数结构，不动一个字段
- 复用 `markBuy(i, deltaG, px)`，兜底本质就是一次增量买入
- 复用 `swingGears` 判断角色：`isSwingGear(i)` 为真则跳过

**P6 的 `gearMarks` 结构从本期起冻结。**

## 4. 计算规则

### 4.1 谁是「下一个待买档」

```js
function dripNext(){
  // 按档号从小到大，第一个满足「不是循环档 且 待补 > 0.05」的档
}
```

只返回一个档号。**同一时刻最多只有一条兜底提示** —— 不允许 4 档和 5 档同时弹，那样用户不知道该买哪个。

### 4.2 计时写入（`tickDrip`）

在 `compute()` 末尾调用，纯写不渲染：

```
next = dripNext()
if next 存在:
    if !dripAt[next] → dripAt[next] = now        // 首次成为下一个待买档，开始计时
    其余档的 dripAt 全部删除                      // 只有当前这一个在计时
else:
    dripAt = {}                                  // 全买满了，清空
```

三个明确规则：

| 情形 | 处理 | 理由 |
|---|---|---|
| 价格反弹回浅档、该档不再是下一个待买档 | `dripAt` **删除** | 它已经不在队列首位，计时没有意义；等它再回到首位时重新起算 |
| 该档被买满 | 删除 | 同上 |
| 改 H / α / 档距导致档位价变化 | **保留** `dripAt` | 等待是客观事实，不因参数调整而作废 |

> 与 P5 §13.4 的一处差异：P5 写的是「反弹回浅档时 dripAt 不清零」。P7 改为**清掉**。理由：P5 假设 4 档一直在等，但实际是「下一个待买档」在轮换 —— 4 档没有被触发时 5 档也不该计时，否则 30 天后会同时到期的有 4 个。谁来等，谁计时。

### 4.3 判定能否提示

```js
function dripInfo(i){
  // 返回 { armed, days, premium, pending, gram, amt, canPrompt, why }
}
```

判定顺序（任一条不满足就不提示，并在 `why` 里给出原因）：

| # | 条件 | 不满足时 |
|---|---|---|
| 1 | `cfg.dripDays > 0` | 功能已关闭 |
| 2 | `isSwingGear(i) === false` | 循环档不兜底 |
| 3 | `i === dripNext()` | 还没轮到这一档 |
| 4 | `pending > 0.05` | 已买满 |
| 5 | `days >= dripDays` | 还差 N 天 |
| 6 | `premium <= dripMaxPremium` | 现价高于档位 X%，追高不如等 |

`premium = (S.price / 档位价 - 1) * 100`，用 `S.price`（页面现价），不用分时价。

### 4.4 兜底克重与金额

```
gram = pending * dripPct
if (gram < 1) gram = pending          // 尾数保护：不足 1g 就一次清掉，避免 0.3g 这种碎片
amt  = gram / 31.1035 * S.price
```

尾数保护的理由：待补剩 1.2g、比例 50% 时算出 0.6g，买入没有意义，且会无限次触发。

### 4.5 数值示例（基准参数，可复现）

场景：1/2/3 档已买满（88g），现价 3960，第 4 档 3945 已等 32 天。

- `premium = (3960 / 3945 - 1) × 100 = +0.38%` ≤ 3% → 可提示
- `pending = 72g`，`gram = 36g`
- `amt = 36 / 31.1035 × 3960 = 4583.4 美元`

执行后的整体效果：

| 项 | 兜底前 | 兜底后 |
|---|---|---|
| 持仓 | 88 g | 124 g |
| 累计成本 | 11383.7 | 15967.1 |
| 均价（$/oz） | 4023.5 | **4005.1** |

**36g 按现价买进去，把整体均价拉低了 18.4 美元。** 这就是兜底的实际价值 —— 不是赚，是"让钱开始工作"。

再等 30 天如果还是没到 3945，第二次兜底买剩下的一半（18g），均价继续小幅下移。指数收敛，永远不会把 72g 一次打光。

### 4.6 溢价容忍的实际含义

第 4 档 3945，容忍 3% → 触发上限 3945 × 1.03 = **4063.35**。

- 现价 4030 → 溢价 2.15%，**会提示**（在容忍内）
- 现价 4080 → 溢价 3.42%，**不提示**（追高不如等）

> 注意：P5 文档里「现价 4030 溢价 4.2%」是按旧档位价 3867.6 算的。按当前参数（H=4700、d=48）第 4 档是 3945，同样的 4030 只有 2.15%。参数变了，结论跟着变，文档以本文为准。

## 5. 交互

### 5.1 档位行（`renderLadder`）

在建仓档的行下方插入一条提示条，**只在该档可提示时出现**：

```
┌────────────────────────────────────────────┐
│ 已等 32 天 · 距档位 +0.4%      [按现价买 36g] │
│ 3 档已满仓，4 档是下一个目标                  │
└────────────────────────────────────────────┘
```

未到期时不给任何常驻文案（避免界面被"还差 12 天"这类噪音占满）。用户想看进度，到设置页看汇总行。

### 5.2 设置页

在「循环档」区块下新增一组：

```
深档兜底
[等待天数 30]  [兜底比例 0.5]  [溢价容忍 3%]
当前：第 4 档已等 32 天，到期可买 36g
关掉等待天数（填 0）即关闭此功能
```

三格输入，`type="number"` + `inputmode="decimal"`，与既有设置项风格一致。底部一行只读状态，显示当前计时档与天数。

### 5.3 执行后的反馈

点「按现价买 36g」→ 立即写 `markBuy` → `refreshAll()` → 提示条消失 → `toast("已按 3960 买入 36g，第 4 档剩余 36g")`。

不弹二次确认：这个操作可撤销（P6 的卖出/撤销标记通道在），加确认框只会增加摩擦。

### 5.4 空态

- 账本模式：整块不出现
- 计划模式但全部买满：不出现
- `dripDays = 0`：不出现，设置页也没有状态行

## 6. 边界与提示

| 边界 | 处理 |
|---|---|
| 页面不打开就不计时 | 计时靠 `compute()` 触发，下次打开时按真实时间差补算，不会漏 |
| 用户改本地时间 | 允许，只是提示来早/来晚，无数据风险 |
| `dripAt` 因同步失败丢失 | 重新从「首次成为下一个待买档」起算，最坏情况是晚 30 天提示 |
| 现价为 0（行情未加载） | `premium` 算不出 → 不提示 |
| 待补 0.5g | 尾数保护，一次清掉 |
| 循环档被用户勾到 3–6 档 | 该档不再兜底（先满足循环，兜底让位）。设置页保留 P6 已有的橙字提醒 |
| 清空数据 | `dripAt` 一并清空 |

## 9. 风险与未决

| 风险 | 影响 | 缓解 |
|---|---|---|
| 用户不打开页面 → 计时不推进 | 提示会晚到 | 计时按真实时间差补算，不是「打开次数」；文案不承诺"准时提醒" |
| `dripAt` 存在 cfg 里随同步走 | 多端一致，无冲突 | 时间戳以最新覆盖，无需合并 |
| 兜底被滥用（每 30 天点一次，把深档买满） | 均价拉低效果打折 | 这是用户的选择，不算 bug；设置页说明「比例越小越保守」 |
| 与 P6 循环档同时开满 6 档 | 逻辑冲突 | `dripInfo` 第 2 条硬拦，循环档永不走兜底 |

### 待你拍板的四处（可全部按推荐默认）

| # | 问题 | 推荐 |
|---|---|---|
| 1 | 兜底比例默认 50%？ | 是。30% 太保守（要 4 次才买满），70% 偏激进 |
| 2 | 允许反复触发（每次一半）？ | 是。指数收敛，不会一次打光 |
| 3 | 账本模式是否显示只读等待天数？ | **不显示**。账本模式没有「计划待补」概念，显示会误导 |
| 4 | 提示条放行内还是卡片顶部汇总？ | 行内。放在对应档位旁边，用户才知道点的是哪一档 |

## 12. 实施记录（v6.20 · 2026-10-30）

两期一起落地，全量 **388 条测试全绿**（P6 基线 343 + 本期新增 45）。

### 12.1 与本文档的差异

| # | 文档原方案 | 实际做法 | 理由 |
|---|---|---|---|
| 1 | §4.3 `premium > dripMaxPremium` 才算超限 | `premium > max + 1e-9` | 现价正好等于「档位价 × 1.03」时算出 3.0000000000000004，会被误判成超限。容忍线是「不超过」，浮点误差不该改变结论 |
| 2 | §5.1 提示条文案「距档位 +0.4%」 | 「还差 0.4%」/「已低于档位 0.4%」 | 带正负号的百分比要用户自己换算方向，不如直接说清是「还没到」还是「已经跌穿」 |
| 3 | §3.2 `cleanDripAt` 顺带删除「已买满」的计时 | 只做格式清洗，「买满删除」交给 `tickDrip` | 清洗阶段调 `planOf/boughtOf` 会形成初始化依赖；每次 `compute` 重算更简单也不会漏 |
